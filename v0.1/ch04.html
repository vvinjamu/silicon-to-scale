Memory Hierarchy & HBM Deep Dive

The Physical Foundation of Every GPU Performance Decision — From Registers to Clusters, and the Kernel That Changed Everything: Flash Attention v1 → v2 → v3
Book: AI/ML Infrastructure from Silicon to Scale — V2 Edition  |  Author: Venkat Vinjam  |  Cross-ref: Ch 1: Roofline Ch 7: GPU Kernels Ch 11: KV Cache
"GPUs don't run out of compute. They run out of memory bandwidth. Every performance optimization in AI infrastructure is, at its core, a battle against the memory wall." — Principal Performance Architect's First Principle

This chapter answers one deceptively simple question: Why is moving data harder than computing with it? The answer determines whether a kernel runs at 5% or 95% hardware efficiency, whether an inference system serves 10 users or 10,000, and whether your cluster achieves 40% or 80% Model FLOP Utilization (MFU).

4.1 The Memory Wall — Why It Exists and Won't Go Away

The Widening Gap Compute grew ~20× from V100→B200 over 6 years. Bandwidth grew only ~9×. The compute:bandwidth ratio widened from 124→562 FLOP/byte. Operations that were compute-bound in 2018 may now be memory-bound on H100. Performance engineers must constantly re-evaluate which regime their operations fall into as GPU generations advance.

Why bandwidth is hard to scale: Pin count physics limits each data pin to ~64 Gbps. DRAM refresh overhead consumes 3–5% at room temperature, rising to 8–12% at AI datacenter temperatures. The H100's HBM3 interface consumes ~40–60W just for the memory subsystem before any compute. HBM addresses these constraints by stacking DRAM dies vertically with through-silicon vias (TSVs), enabling 1024-bit buses at lower voltage — dramatically better bandwidth-per-watt and bandwidth-per-area than GDDR memory.

4.2 The Five-Tier GPU Memory Hierarchy

Every performance optimization involves moving data to the fastest tier that can hold it.

TIER 1
Registers

~33 MB total (H100) · 1-cycle latency · unlimited bandwidth

65,536 × 32-bit registers per SM. Critical: register pressure limits occupancy. At 64 regs/thread → 50% occupancy; at 128 regs → 25%. Register spilling maps overflow to HBM L2 — turning 1-cycle access into 200–800 cycle access, a 200–800× slowdown.

TIER 2
L1/SMEM

228 KB/SM · ~80–100 TB/s aggregate · 20–30 cycle latency

Explicitly programmer-managed cache shared among threads in a block. The key mechanism for GEMM tiling: without SMEM tiling, every operand access goes to HBM. Bank conflicts (32 banks, 4-byte words) can reduce SMEM BW from peak to peak/32. Fix by padding inner dim: smem[32][33] instead of smem[32][32].

TIER 3
L2 Cache

50 MB · ~12 TB/s aggregate · 200–400 cycle latency · all SMs share

Hardware-managed. Limited benefit for decode (weights far exceed 50 MB). Useful for KV cache hot-path, embedding table lookups, LayerNorm running stats. L2 hit rate in Nsight Compute indicates streaming vs. reuse patterns.

TIER 4
HBM

80–192 GB per GPU · H100: 3.35 TB/s | H200: 4.8 TB/s | B200: 8.0 TB/s · 400–800 cycle latency

Per-GPU global memory. Holds model weights, activations, KV cache — the primary bottleneck for all memory-bound operations. Achieving >80% utilization requires coalesced access, tiling, and quantization.

TIER 5
Host DRAM

1–2 TB per server · PCIe Gen5: 128 GB/s GPU↔CPU · 10,000–50,000 cycle GPU latency

CPU memory. Dataset staging, checkpoint buffers, model spill. PCIe is 26× slower than HBM. Frequent GPU↔CPU transfers are catastrophic for performance — minimize at all costs.

SMEM TILING — Naive GEMM vs Tiled GEMM: Naive GEMM: For each (i,j) in C[M×N], for each k in K: Load A[i,k] from HBM + Load B[k,j] from HBM (2 reads per multiply) Total reads M=N=K=4096: 137 billion HBM reads → fully bandwidth-bound Tiled GEMM (SMEM): Load TILE_M×TILE_K block of A + TILE_K×TILE_N of B into SMEM once, compute all inner products from SMEM (fast access). TILE=128: HBM reads reduced by 128× · AI rises to 128 FLOP/byte → compute-bound ✓

Why HBM capacity scales slowly: Three constraints limit adding stacks: (1) Silicon interposer area is bounded by reticle limits (~858 mm²). (2) TSV yield — thousands of 55 μm-pitch vias per stack; defect rates multiply with taller stacks. (3) Thermal extraction — each stack dissipates 5–10W internally, running 15–25°C hotter than the GPU die. These drive ~2× capacity growth per generation vs. ~3× compute growth.

Coalesced vs. Uncoalesced Access — The #1 Pattern Decision When 32 threads access 32 consecutive 4-byte addresses (128 bytes = 1 cache line): ONE HBM transaction → 100% efficiency.
When 32 threads access 32 different cache lines: up to 32 separate transactions → 3% efficiency — a 32× overhead.

Fix: Ensure thread i accesses base + i × element_size. Avoid column-major traversal of row-major arrays. For GEMM B^T: store B transposed so both A and B^T are row-traversed.

4.4 The Arithmetic Intensity Framework

Arithmetic Intensity (AI) Definition AI = FLOPs executed / Bytes transferred to/from HBM  [units: FLOP/byte]
This single number determines whether any operation is memory-bound or compute-bound on any given hardware.
KEY LLM OPERATIONS — ARITHMETIC INTENSITY: GEMM (prefill): C[M×N] = A[M×K] × B[K×N] FLOPs: 2×M×N×K · Bytes: (M×K + K×N + M×N) × dtype_bytes M=N=K=4096, BF16: FLOPs=137.4G · Bytes=100.7M → AI=1,365 FLOP/byte H100 ridge=295 → compute-bound ✓ (This is why large-batch prefill is fast) GEMV (decode, batch=1): y[M] = A[M×K] × x[K] FLOPs: 2×M×K · Bytes: M×K × dtype_bytes (load ENTIRE weight matrix!) M=K=8192, BF16: FLOPs=134.2M · Bytes=134.2M → AI=1.0 FLOP/byte H100 ridge=295 → DEEPLY MEMORY BOUND ✗ (decode loads weights for 1 token) RMSNorm / LayerNorm: AI ≈ 1.25 FLOP/byte → memory-bound Practical throughput: HBM_BW/4 = 3.35TB/s/4 ≈ 840 GB/s of elements → Standalone normalization wastes 99.6% of compute capacity → Operator fusion with adjacent GEMM is MANDATORY Softmax (attention row, standard): AI ≈ 5 FLOP/byte → memory-bound FlashAttention QK matmul (S=2K): AI ≈ 250 FLOP/byte → near-ridge Attention GEMM S=4096: AI ≈ 2048 FLOP/byte → compute-bound Roofline rule (H100 BF16, ridge=295): If AI < 295: achievable TFLOPS = AI × 3.35 If AI > 295: achievable TFLOPS = 989 (compute ceiling)

4.8 Flash Attention — A Complete Deep Dive

"Flash Attention is not a clever trick. It is the correct way to implement attention. Everything else is wrong in proportion to how much memory it wastes." — AI Systems Engineering Perspective

Flash Attention is the single most impactful GPU kernel innovation of the LLM era. Every major production system — vLLM, TRT-LLM, Megatron-LM, HuggingFace Transformers — uses it by default.

4.8.1 The Problem: Standard Attention Is O(N²) in Memory

STANDARD ATTENTION HBM TRAFFIC (Q,K,V each [N×d]): Step 1: S = Q × Kᵀ / √d → S [N×N] WRITE to HBM Step 2: P = softmax(S) → P [N×N] READ + WRITE to HBM Step 3: O = P × V → O [N×d] READ + WRITE to HBM Total: 4×N×d + 3×N² bytes (BF16: ×2) For N=4096, d=128, BF16: N×d terms: 4 × 4096 × 128 × 2 = 4.2 MB N² terms: 3 × 4096² × 2 = 100.7 MB ← DOMINATES Total per head: ~105 MB For LLaMA-3 70B (80 layers × 64 MHA heads): 80 × 64 × 105 MB = 537 GB HBM traffic for attention alone! At H100 3.35 TB/s: 0.16 seconds minimum per fwd pass (memory only!) CONTEXT LENGTH SCALING (why long contexts need FA): N=8192: N² = 134 MB/head → problematic N=32768: N² = 2.1 GB/head → can't fit in 80 GB HBM N=128K: N² = 32 GB/head → physically impossible → Standard attention CANNOT support long contexts

4.8.2 The Key Insight: Online Softmax

Standard softmax for row i requires ALL j values simultaneously — the denominator requires the full sum. Online softmax (Milakov & Gimelshein, 2018) maintains running statistics correctable tile-by-tile.

ONLINE SOFTMAX TRICK: For row x processed in tiles [x₁..xₖ] then [xₖ₊₁..xₙ]: AFTER TILE 1: m₁ = max(x₁..xₖ) ← running maximum ℓ₁ = Σ exp(xⱼ - m₁) ← partial denominator (stable) O₁ = Σ exp(xⱼ - m₁) × Vⱼ / ℓ₁ ← partial output AFTER TILE 2 (with correction): m₂ = max(m₁, max(xₖ₊₁..xₙ)) ← global max update α = exp(m₁ - m₂) ← correction factor for old partial sum ℓ₂ = α × ℓ₁ + Σ exp(xⱼ - m₂) ← updated denominator O₂ = (α × ℓ₁ × O₁ + Σ exp(xⱼ - m₂) × Vⱼ) / ℓ₂ RESULT: O₂ is MATHEMATICALLY IDENTICAL to softmax([x₁..xₙ]) × [V₁..Vₙ] — computed WITHOUT ever materializing the N×N matrix! NUMERICAL STABILITY: Naive exp(1000) = inf (overflow), exp(-1000) = 0 (underflow) Online softmax subtracts running max m: keeps all values in [exp(-large), 1] This stability property is preserved across tiles via the correction factor α.
