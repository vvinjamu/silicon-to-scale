Deep Technical Questions — Apple GPU Architecture

Expected Q — TBDR Architecture
"Explain how Tile-Based Deferred Rendering works and what performance implications it has."

Your Answer:

TBDR splits rendering into two passes. Pass 1 (Binning / Tiling): The GPU processes all geometry, determines which triangles touch which screen tiles (typically 32×32 pixels), and records only primitive metadata — no shading. Pass 2 (Rendering): Each tile is loaded into on-chip tile memory, all pixels in that tile are fully shaded, then the completed tile is written back to main memory.

Performance implications:

  • Hidden surface removal before shading: Pixels occluded by opaque geometry never run the fragment shader. On a dense scene this is a major compute saving.
  • Bandwidth saving: The framebuffer never leaves the tile memory during a render pass. Depth buffer, color buffer, and MSAA samples all live on-chip. Main memory only sees the final resolved color — massive bandwidth reduction vs. immediate-mode.
  • Latency sensitivity: All geometry must be submitted before shading begins. This creates a binning bottleneck on geometry-heavy scenes. A perf analyst must profile whether the binning pass or the rendering pass is the limiter.
  • Bridge to my experience: "This is architecturally the same principle as the shared memory tiling I apply to GEMM kernels — maximize on-chip data reuse before going to main memory. The TBDR tile IS shared memory for the rendering pipeline."
Expected Q — UMA Bandwidth Contention
"In a UMA system where GPU and CPU share memory bandwidth, how do you profile and isolate GPU bandwidth consumption?"

Your Answer: "On a UMA system, the memory controller is the shared resource. You need system-level bandwidth profiling, not just GPU-level. On Apple SoCs, Instruments gives you per-client bandwidth visibility — GPU, CPU, ANE each appear as bandwidth consumers. The technique: profile the workload under two conditions: (1) GPU running alone (CPU parked), and (2) CPU+GPU concurrent. The delta in GPU throughput is bandwidth contention loss. I've done exactly this analysis on Intel Ultrabook platforms where iGPU and CPU cores compete for the LPDDR4 bus. At Intel I found that aggressive CPU prefetch patterns were stealing 15% of iGPU effective bandwidth on multimedia playback — fixed with a BIOS-level arbitration weight change."

Expected Q — Hardware Feature Proposal Process
"Walk me through how you'd propose a novel hardware feature to improve GPU performance."

Your Answer: "The proposal has four components: (1) Empirical bottleneck identification — show with counter data that the bottleneck is real and recurring across the target workload class. (2) First-principles model — derive the expected speedup from the proposed change using a roofline or latency model. Be explicit about assumptions. (3) Workload coverage analysis — quantify what fraction of shipped workloads would benefit. A feature that helps 5% of workloads doesn't justify silicon area. (4) Area/power estimate — at minimum a rough order-of-magnitude estimate so the architecture team can evaluate the trade-off. At AMD I've done this for cache prefetch policy and tiling configuration changes. The credibility comes from showing the data, not just the idea."

Expected Q — Occupancy and Threadgroup Sizing
"How do you reason about GPU occupancy, and when does maximizing occupancy NOT help performance?"

Your Answer: "Occupancy measures how many active wavefronts/SIMD groups are resident on an execution unit. High occupancy is valuable when you're latency-bound — more resident warps means the scheduler can hide ALU and memory latency. But in a compute-bound kernel, you may already have enough warps in flight, and adding more occupancy just increases register pressure, which reduces register file per thread and may spill to local memory. The way to diagnose: look at IPC (Instructions Per Clock) vs. stall cycles. If memory latency dominates stall cycles and IPC is low, occupancy may help. If the kernel is compute-saturated (high IPC, low stall), occupancy is irrelevant and optimizing register use for cache performance matters more. On AMD CDNA I use omniperf's occupancy vs. IPC scatter plots to make this call automatically."

The Profiling Methodology — Your Standard Approach

1
Timeline View — Find the Macro Pattern
Instruments GPU Timeline / Counters Timeline

Open timeline, look for: idle gaps between GPU submissions (CPU-side stall), sustained GPU activity with low throughput (compute or BW bound), or irregular texture/render pass transitions. This tells you whether the problem is in submission overhead or within kernel execution.

2
Regime Classification — BW, Compute, or Latency Bound
GPU counters: memory read/write BW, shader utilization, occupancy

Compute achieved BW vs. peak BW. Compute achieved FLOPS vs. peak FLOPS. This classifies the kernel into one of three regimes. On Apple, TBDR adds a 4th: binning-bound (geometry throughput limited, shader units idle).

3
Root Cause — Counter Drill-Down
Shader stall reasons, cache hit rates, pipeline utilization per stage

If memory-bound: L1/L2 hit rates, texture cache utilization, bandwidth client breakdown (texture vs. shader vs. tile reads). If compute-bound: instruction mix, ALU vs. SFU utilization, vector vs. scalar ratio. If latency-bound: occupancy, scheduler efficiency, memory queue depth.

4
Hypothesis → Fix → Validate
Always measure the fix, never just assume it worked

Formulate a specific hypothesis ("L2 miss rate is high because threadgroup size exceeds working set; reducing to 16×16 should fit in L1"). Implement the change. Re-measure the same counters. Quantify the speedup. Document for the hardware team if it reveals a microarchitectural opportunity.

Counter Interpretation — Key Questions to Answer

Memory Bandwidth Analysis
  • Achieved BW / Peak BW = bandwidth utilization %
  • L1 hit rate: >90% = well-tiled; <60% = re-examine access pattern
  • L2 hit rate: >80% = working set fits; lower = memory-bound
  • On TBDR: tile memory read/write separate from system BW
  • UMA contention: CPU bandwidth during same interval
Compute Throughput Analysis
  • Shader occupancy: active SIMD groups / maximum
  • ALU utilization vs. SFU utilization (transcendentals expensive)
  • Warp stall reasons: memory dependency, scoreboard, sync
  • Vector vs scalar instruction ratio (scalar = single-thread path)
  • Register spills → local memory → bandwidth spike

Classic Debug Scenarios — Be Ready to Walk Through

Scenario A — Regression in a Render Pass After Driver Update

"New driver version shows 15% regression in render pass time. Geometry is unchanged. Where do you look first?"

Your approach: First check if the regression is in binning or rendering phase (TBDR split). If rendering: compare shader instruction counts before and after — a compiler change may have introduced a register spill or unrolled a loop differently. Check L2 hit rate — a cache policy change could degrade locality. Check fragment shader occupancy — if the new driver is allocating more registers per thread, occupancy drops and latency hiding degrades. Always isolate to a single draw call or pass using GPU Frame Capture before generalizing.

Scenario B — ML Inference Kernel Slower Than Expected

"A Metal Compute kernel for a GEMM-like ML layer achieves only 40% of theoretical throughput. Walk me through the diagnosis."

Your approach: Calculate arithmetic intensity: FLOPs = 2 × M × N × K; Bytes = (M×K + K×N + M×N) × element_size. Compare to ridge point (~26–37 FLOP/byte on Apple). If below ridge, it's memory-bound — focus on tile size and threadgroup memory usage. If above ridge and still slow, check occupancy (register pressure? threadgroup memory size?), check instruction issue efficiency, check if the workload is using the right data type (FP16 vs FP32 ALUs). On Apple, check if MPS has an optimized version of this operation — if so, compare to it as a reference.

Problem 1 — Novel Feature Proposal
"Propose a hardware feature that doesn't exist today that would meaningfully improve GPU performance in a specific use case you care about."

Your Answer — Be specific and data-driven:

Proposal: Adaptive Tile Size for TBDR Based on Scene Complexity Feedback

Current Apple TBDR uses fixed tile sizes (typically 32×32). In scenes with many small triangles (UI, text rendering, particle systems), the binning pass overhead is high relative to the tile rendering work — lots of small primitives map to many tiles. In scenes with few large triangles (background blur, simple geometry), the binning pass is cheap but tiles may be large and efficient.

Proposed feature: A hardware feedback register that reports binning-to-rendering time ratio per render pass. The driver/API could use this to dynamically adjust tile size: smaller tiles for geometry-heavy scenes (more parallelism, less per-tile work) vs. larger tiles for simple scenes (better locality). The counters to validate this already exist — binning pass duration vs. rendering pass duration. I would build a microbenchmark varying triangle count and scene complexity, measure the binning-to-rendering ratio, model the speedup from tile size adaptation, and present the workload coverage analysis.

Note: If the interviewer says this exists already, respond: "That's excellent — I'd love to understand how it's implemented. Does the feedback mechanism live in hardware or is it driver-managed heuristics?"

Problem 2 — First Principles Estimation
"Estimate the memory bandwidth required to run a real-time diffusion model (e.g., image generation) at 30fps on an iPhone."

Thinking out loud:

A typical mobile diffusion model (Core ML / Apple ANE-optimized) has ~500M–1B parameters at INT8 = 500MB–1GB model weights. Diffusion runs 20–50 denoising steps. Each step is effectively a UNet forward pass. Let's model this:

Params: 500M × 1 byte (INT8) = 500 MB model
Per-step BW: read weights (500 MB) + activations (~100–200 MB) ≈ 700 MB/step
30fps × 20 steps = 600 denoising steps/second
Required BW: 700 MB × 600 = 420 GB/s continuous

Apple A18 Pro memory BW: ~68 GB/s total
→ This CANNOT run on iPhone at 30fps from DRAM alone.

Resolution: (1) Reduce steps (distillation → 4–8 steps)
(2) Quantize to INT4 → 4× BW reduction → ~105 GB/s → still 1.5× over budget
(3) Route to ANE which has dedicated weights cache
(4) Run at lower res, upscale with FSR-equivalent

Conclusion: Real-time diffusion on iPhone is a bandwidth engineering problem, not a compute problem. The answer reveals why Apple's ANE has a dedicated model weight cache — it breaks the DRAM bandwidth wall.

Problem 3 — Architectural Trade-off
"For a mobile SoC GPU, would you increase the number of shader cores or increase the L2 cache size? Argue both sides, then give your answer."

More cores argument: More compute throughput for compute-bound workloads. Better parallelism for thread-heavy graphics. Direct benefit for any non-bandwidth-limited task.

More L2 argument: On a bandwidth-constrained UMA system, bandwidth is more often the bottleneck than compute. More L2 reduces DRAM traffic, which benefits ALL workloads including the ones that look compute-bound but are actually waiting on memory latency. L2 hits cost ~50 cycles vs. DRAM's ~200+ cycles.

My answer: For a mobile SoC in 2025 where LLM inference, image generation, and real-time ML are the growth workloads — all of which are severely memory-bandwidth-bound at INT8/INT4 precision — I'd take the L2 increase. But with a condition: only if it also serves the ANE and the neural engine memory path. A shared L2 that all compute engines can hit is worth more than a GPU-private one. The right answer depends on what fraction of workloads are already compute-saturated, and on Apple's SoC that fraction is low for the workloads that matter most right now.

Apple GPU Architecture — Technical Reference

The key concepts you must understand before your first session

TBDR — Tile-Based Deferred Rendering Deep Dive

How TBDR Works
  1. Geometry submission: App submits draw calls with vertex + index data
  2. Binning pass: GPU processes all vertices, determines per-tile primitive list (no pixel shading yet)
  3. Tiling: Screen divided into 32×32 pixel tiles (typical)
  4. Rendering pass: For each tile — load tile data to on-chip SRAM → shade all fragments → hidden surface removal → resolve → write finished tile to framebuffer memory
TBDR Performance Benefits
  • Zero bandwidth for framebuffer during render: depth + stencil + MSAA all on-chip
  • Hidden surface removal before shading: occluded pixels never run fragment shader
  • MSAA nearly free: resolve happens on-chip, only final image goes to memory
  • Programmable blending: read-modify-write of tile memory is cheap vs. read-modify-write of DRAM
  • Load/store actions: explicit control of what enters/leaves tile memory
⚠ TBDR Hazards — Common Perf Issues

Forced render pass splits: Certain operations force the GPU to flush the tile — reading the framebuffer mid-pass (e.g., for screen-space effects). This causes a round-trip to memory. Instruments will show this as a "store/load" pair mid-pass.

Geometry overdraw in binning: Too many triangles covering the same tile means the binning pass is bottlenecked. The tile primitive list overflows, causing spills to memory.

Large triangle lists per tile: UI layers with many tiny elements, text, particles — all create expensive binning passes relative to rendering work.

Depth prepass trade-off: On IMR (PC GPUs), depth prepass saves shading cost. On TBDR, the hardware already does HSR — an explicit depth prepass adds binning overhead with potentially no benefit. Measure before assuming.

Apple Unified Memory Architecture (UMA)

Total SoC BW budget (A18 Pro): ~68 GB/s
Clients: CPU cores + GPU + ANE + ISP + Display engine

GPU peak BW consumption = min(GPU_demand, SoC_BW − other_clients)
Contention loss = GPU_demand − GPU_allocated_BW
UMA Performance Engineering Rules
  • Zero-copy is default: CPU and GPU share physical addresses — no memcpy needed for shared buffers. This is a major design win over discrete GPU setups.
  • CPU-GPU coherency has cost: If CPU writes a buffer while GPU reads it, cache coherency protocol runs. Use Metal buffer storage modes correctly: shared vs. private vs. managed.
  • BW contention is invisible by default: GPU may appear compute-bound when it's actually stalled on BW arbitration. You must check system-wide BW counters, not just GPU-side.
  • ANE and GPU can run concurrently: For ML inference pipelines, overlapping ANE and GPU execution is possible. Profile whether their BW demands sum within the budget.

Key Metal API Concepts — Minimum You Must Know

Metal render pipeline: MTLRenderCommandEncoder → submit draw calls within a render pass descriptor. The render pass descriptor defines load/store actions for each attachment. Key perf tip: Always set loadAction to .dontCare if you're writing every pixel, and storeAction to .dontCare for depth/stencil if you don't need them after the pass. This tells the TBDR driver to skip unnecessary loads/stores to memory.

Metal compute pipeline: MTLComputeCommandEncoder → dispatch threadgroups. Threadgroup memory = Apple's equivalent of CUDA shared memory / AMD LDS. Size up to device limits (typically 32KB). Thread execution width (SIMD group size) is queryable — important for occupancy math. Metal Compute is the API for ML inference kernels, image processing, physics simulation.

Metal has three buffer storage modes: shared (CPU and GPU both access, coherent, slightly slower for GPU), private (GPU only, fastest GPU access, no CPU mapping), managed (macOS only — separate CPU/GPU copies with explicit sync via didModifyRange). On Apple Silicon with UMA, shared is often the best choice since there's no physical copy overhead.

Metal synchronization: MTLFence (within a command queue, signal/wait), MTLEvent (cross-queue, cross-device). MTLSemaphore for CPU-GPU synchronization. Over-synchronization is a common perf mistake — inserting fences between every pass serializes the GPU pipeline unnecessarily. Profile command buffer completion timing before adding sync barriers.

Power-Performance Reasoning — Mobile First

The Mobile Constraint Model

Phone thermal envelope: ~3–7W sustained GPU power. At peak (burst) maybe 10–12W for 1–2 seconds before thermal throttle. Performance analysis on mobile must always ask: "Is this workload sustainable at this throughput, or will it throttle?"

Sustained throughput ≈ f(thermal_budget, power_efficiency)
Power = Capacitance × V² × frequency + leakage
DVFS: lower V and f = quadratic power reduction, linear throughput reduction

Key metric: Performance per Watt, not absolute TFLOPS
Apple M4 Pro: ~150 GFLOPS/W (FP32) vs. H100: ~220 GFLOPS/W (with SXM)

Could Be Asked — Tiled Matrix Multiply in Metal

Be ready to sketch the algorithm, not write perfect syntax:

// Metal compute kernel — tiled GEMM
kernel void tiledGEMM(
    device float* A [[buffer(0)]],
    device float* B [[buffer(1)]],
    device float* C [[buffer(2)]],
    threadgroup float* tileA [[threadgroup(0)]],  // 32KB shared
    threadgroup float* tileB [[threadgroup(1)]],
    uint2 tid [[thread_position_in_threadgroup]],
    uint2 gid [[threadgroup_position_in_grid]])
{
    // Load tile of A and B into threadgroup memory
    tileA[tid.y * TILE + tid.x] = A[...];
    tileB[tid.y * TILE + tid.x] = B[...];
    threadgroup_barrier(mem_flags::mem_threadgroup);
    
    // Compute partial dot product from tiles
    float acc = 0.0;
    for (uint k = 0; k < TILE; k++)
        acc += tileA[tid.y * TILE + k] * tileB[k * TILE + tid.x];
    
    C[global_row * N + global_col] = acc;
}

Key insight to mention: tile size choice trades off threadgroup memory pressure vs. L2 miss reduction. Optimal tile = sqrt(threadgroup_memory / 2 / sizeof(float)). On Apple with 32KB threadgroup memory: tile = 64.

Whiteboard / Problem-Solving Prep

Apple Whiteboard Philosophy Apple interviewers are not looking for memorized answers. They're watching how you think. Always narrate your reasoning. Draw diagrams. Ask clarifying questions. Show the math. It's OK to say "Let me think through this step by step."

Problem Type 1 — Performance Estimation (Fermi Problem)

Example: "How much memory bandwidth does a 60fps UI compositor use on iPhone?"

Walk through out loud:

  1. iPhone 16 Pro: 2796×1290 pixels @ 60fps (up to 120Hz ProMotion)
  2. UI compositor reads: screen layers. Typical scene: 5–10 layers composited
  3. Per frame: read 5 layers × 2796×1290 × 4 bytes (RGBA32) + write 1 output frame
  4. = 5 × 14.4 MB + 14.4 MB = 86 MB/frame
  5. At 60fps: 86 MB × 60 = 5.16 GB/s
  6. At 120fps: ~10 GB/s
  7. That's ~15% of the A18 Pro's total BW budget just for UI compositing at 120fps

Insight: This is why Apple invests in TBDR, display compression (LPDP), and hardware compositing accelerators — raw compositing at this resolution is BW-expensive.

Problem Type 2 — Debug Walkthrough

Example: "A Metal app that was 60fps on A17 Pro is only 45fps on A18 Pro with the same workload. What's going on?"

Your structured approach:

  1. First, verify the claim: Is the hardware the same configuration? Same thermal state? Same OS? Is the regression reproducible?
  2. Check obvious candidates: A18 Pro may have a different driver/compiler. GPU core count may be same (both 6-core) but clock frequency or power policy may differ.
  3. Profile with Instruments: Is the GPU the bottleneck, or is it CPU submission overhead? If GPU is at 100% utilization in both cases but A18 is slower — possible clock throttle. If GPU is <100% — CPU-bound or submission overhead.
  4. Check power/thermal: A18 Pro has a new power management policy. It may sustain lower GPU clocks under thermal load. Check Energy Log for throttle events.
  5. Hypothesis: Compiler regression. A17 → A18 driver update may have changed shader codegen. Compare shader assembly between A17 and A18 builds using GPU Frame Capture shader inspection.
  6. Resolution path: File bug with minimal reproducer + counter data + expected vs. actual perf. If throttle-related, work with power team.

Problem Type 3 — Design Question

Example: "Design a performance test suite for validating a new GPU hardware feature."

Your answer structure:

  1. Define the feature: What hardware behavior does it change? (e.g., new prefetch unit, wider memory bus, new texture cache size)
  2. Identify the sensitivity surface: What workload characteristics would expose this feature's benefit? (For a prefetch unit: stride-sequential access patterns. For wider bus: bandwidth-saturating workloads.)
  3. Build microbenchmarks first: Isolate exactly the hardware behavior. Sweep the parameter space. Validate that the counters show the expected hardware behavior change.
  4. Build macro benchmarks: Real apps/games that exercise the target workload class. Measure end-to-end impact.
  5. Establish statistical validity: Multiple runs, thermal conditioning, coefficient of variation <2% for reliable regression detection.
  6. Automate: Integrate into CI. Define regression thresholds. Alert on deviations.
