B.2 Nsight Systems (nsys) — System-Level Timeline

Purpose: System-wide timeline showing where wall-clock time goes — kernel launches, memory copies, NCCL collectives, CPU activity. Answer: "Where is the time?"
Overhead: 1.5–3× slowdown. Capture 30–60 seconds in production-equivalent conditions.

Core Commands

# ── STANDARD TRAINING PROFILE ─────────────────────────────────────────────────
nsys profile \
  --trace=cuda,nvtx,nccl,osrt \       # CUDA kernels + NVTX markers + NCCL + OS runtime
  --sample=cpu \                       # CPU call-stack sampling
  --output=/tmp/profile_%p \          # Separate file per rank (%p = PID)
  --duration=30 \                      # 30-second capture window
  python train.py

# ── MINIMAL (lowest overhead) ──────────────────────────────────────────────────
nsys profile --trace=cuda --output=/tmp/trace python script.py

# ── WITH NVTX MARKERS (requires torch.cuda.nvtx.mark() in code) ────────────────
nsys profile --trace=cuda,nvtx --output=/tmp/trace python train.py

# ── ATTACH TO RUNNING PROCESS ─────────────────────────────────────────────────
nsys profile -p $(pgrep python) --duration=30 --output=/tmp/attached

# ── OPEN IN GUI ───────────────────────────────────────────────────────────────
nsys-ui /tmp/profile_12345.nsys-rep

# ── CLI STATISTICS SUMMARY ────────────────────────────────────────────────────
nsys stats /tmp/profile_12345.nsys-rep --report gputrace
# Output: top kernels by duration (% of total GPU time)

What to Look for in the Timeline

ObservationDiagnosisAction
GPU row is dense — no visible gaps✅ Compute-bound or bandwidth-bound — healthyNo action needed; verify with ncu roofline
Gaps > 1 ms between kernels❌ CPU launch overhead or data pipeline stallUse CUDA Graphs or torch.compile to eliminate gaps
NCCL spans overlap backward kernels✅ Gradient communication correctly hiddenMeasure overlap fraction — target > 80%
NCCL spans are sequential after backward❌ Allreduce not overlapped — 10–30% throughput lossEnable gradient_as_bucket_view=True in DDP
CPU idle gaps between GPU launches❌ Data loading bottleneck or Python GILPrefetch with pin_memory=True, increase num_workers
Many tiny kernels (< 50 µs each)❌ Op-by-op execution — poor fusionEnable torch.compile or manual kernel fusion

NVTX Instrumentation (Add to Training Loop)

import torch

# Mark iteration boundaries — nsys shows step time breakdown
for step, batch in enumerate(dataloader):
    torch.cuda.nvtx.range_push(f"step_{step}")

    torch.cuda.nvtx.range_push("data_to_device")
    inputs = batch.to("cuda")
    torch.cuda.nvtx.range_pop()

    torch.cuda.nvtx.range_push("forward")
    loss = model(inputs)
    torch.cuda.nvtx.range_pop()

    torch.cuda.nvtx.range_push("backward")
    loss.backward()
    torch.cuda.nvtx.range_pop()

    torch.cuda.nvtx.range_push("optimizer")
    optimizer.step(); optimizer.zero_grad()
    torch.cuda.nvtx.range_pop()

    torch.cuda.nvtx.range_pop()   # step_N

B.3 Nsight Compute (ncu) — Kernel-Level Hardware Counters

Purpose: Deep hardware counter analysis for a single kernel — Tensor Core utilization, DRAM bandwidth efficiency, SM occupancy, roofline position. Answer: "Why is THIS kernel slow?"
Overhead: 5–20× slowdown. Profile specific kernels, not entire training runs.

Core Commands

# ── FULL KERNEL ANALYSIS ──────────────────────────────────────────────────────
ncu \
  --kernel-name "flash_attention_fwd" \  # Target kernel (regex match)
  --launch-skip 5 \                       # Skip 5 warmup launches
  --launch-count 3 \                      # Profile next 3 launches
  --set full \                            # All hardware counters
  --section SpeedOfLight_RooflineChart \  # Roofline analysis
  --section MemoryWorkloadAnalysis \      # Memory hierarchy breakdown
  -o /tmp/kernel_profile \               # Output file
  python infer.py

# ── QUICK ROOFLINE CHECK ──────────────────────────────────────────────────────
ncu --kernel-name X --set roofline --launch-count 1 python script.py

# ── TENSOR CORE UTILIZATION (key metric for GEMM health) ─────────────────────
ncu --metrics sm__pipe_tensor_cycles_active.avg.pct_of_peak_sustained_elapsed \
    --kernel-name matmul python script.py

# ── OPEN RESULT IN GUI ────────────────────────────────────────────────────────
ncu-ui /tmp/kernel_profile.ncu-rep

# ── COMPARE TWO PROFILES (regression detection) ───────────────────────────────
ncu-ui --diff baseline.ncu-rep current.ncu-rep
# Red = regression, Green = improvement

# ── CSV OUTPUT FOR CI PIPELINES ───────────────────────────────────────────────
ncu --kernel-name X --csv --metrics dram__bytes_read.avg,sm__throughput.avg \
    python script.py > /tmp/metrics.csv

Roofline interpretation: A kernel plotting below and left of the roofline ceiling is bandwidth-bound — more data reuse or tiling can help. A kernel touching the compute ceiling is doing as well as the hardware allows. Tensor Core underutilization with high SM activity usually means FP32 fallback or non-aligned matrix dimensions (must be multiples of 8 for BF16 Tensor Cores, multiples of 16 for INT8).

B.4 DCGM — Fleet GPU Health and the Critical Field IDs

Purpose: Continuous hardware health monitoring across the entire GPU fleet. Exposes temperature, power, ECC errors, clock throttling, and compute activity at 1-second resolution.
⚠ Field 203 (GPU_UTIL) Is Misleading — DCGM field 203 reports the percentage of time any kernel was active, sampled at 1 ms windows. A tiny kernel running for 1 µs every 1 ms reports 100% GPU utilization. Always use field 1003 (SM_ACTIVE) for true compute occupancy.

Essential dcgmi dmon Commands

# ── PRODUCTION HEALTH MONITOR (run continuously) ──────────────────────────────
dcgmi dmon \
  -e 203,1002,1003,1004,1005,1009,100,155,1001 \
  -d 1000 \           # 1-second interval
  -c 3600             # 1-hour capture (drop -c for continuous)

# ── QUICK SPOT-CHECK (all GPUs on node) ───────────────────────────────────────
nvidia-smi dmon -s pucvmet -d 1 -c 30

# ── REMOTE FLEET MONITORING ──────────────────────────────────────────────────
dcgmi group -c training_group
dcgmi group -g 1 -a all
dcgmi dmon -g 1 -e 1003,1004,1005,1009 -d 1000

busbw vs algbw — Which Number Matters?

Use busbw (bus bandwidth) for cluster health assessment. The algbw (algorithm bandwidth) measures bytes sent per second from the application's perspective. The busbw normalizes for the AllReduce algorithm's communication volume — for a ring AllReduce, busbw = algbw × 2(N-1)/N. For a healthy 8-GPU NVLink ring, you expect busbw ≈ algbw × 1.75. If busbw/algbw ratio is wrong, NCCL is using an unexpected algorithm.

🚨 KV Cache Cascade: When vllm:gpu_cache_usage_perc exceeds ~0.85, vLLM begins preempting (evicting) in-flight requests to reclaim KV blocks. B.9 Storage and I/O Diagnostic Commands

Purpose: Diagnose checkpoint I/O bottlenecks, dataset loading stalls, and parallel filesystem (Lustre/GPFS) health. Storage is the silent killer of MFU — a healthy training job loses 2–8% MFU to checkpoint overhead; a sick storage system can stall an entire cluster.

Checkpoint I/O Diagnostics

# ── MEASURE ACTUAL CHECKPOINT WRITE SPEED ─────────────────────────────────────
# Time a checkpoint save directly:
time python -c "
import torch
model = ... # your model
torch.save(model.state_dict(), '/path/to/checkpoint/ckpt.pt')
"
# A 70B BF16 model checkpoint = ~140 GB
# Expected: NFS 10GbE = ~60 sec; Lustre 200 GB/s = ~0.7 sec

# ── FIO SEQUENTIAL BENCHMARK (measure storage peak throughput) ───────────────
# Sequential write (checkpoint scenario):
fio --name=seqwrite --ioengine=libaio --direct=1 \
    --rw=write --bs=4M --numjobs=16 \
    --size=10G --runtime=60 --group_reporting \
    --filename=/mnt/scratch/testfile
# Target for Lustre with 10+ OSS nodes: > 50 GB/s aggregate write

# Sequential read (dataset prefetch scenario):
fio --name=seqread --ioengine=libaio --direct=1 \
    --rw=read --bs=1M --numjobs=32 \
    --size=10G --runtime=60 --group_reporting \

# ── IDENTIFY DATA LOADING BOTTLENECKS IN PYTHON ───────────────────────────────
# Add instrumentation to DataLoader:
import time

class TimedDataLoader:
    def __init__(self, loader):
        self.loader = loader
        self.wait_times = []

    def __iter__(self):
        t0 = time.perf_counter()
        for batch in self.loader:
            wait = time.perf_counter() - t0
            self.wait_times.append(wait)
            yield batch
            t0 = time.perf_counter()

# If avg_wait_ms > 10ms → data loading is bottlenecking GPU
