"Quantization is not about making your model less accurate. It is about using exactly as many bits as the task requires — no more, no less. The difference between FP32 and FP8 for LLM inference is like using a crane to move a pencil."

A 70B parameter model in FP32 weighs 280 GB — more than three H100 GPUs can hold. In FP8, it weighs 70 GB and fits on one. In INT4, 35 GB — with room left over for a generous KV cache and concurrent user pool. Quantization is the engineering discipline of reducing numeric precision without unacceptable quality loss, and it is arguably the highest ROI optimization in modern AI infrastructure: a single change from BF16 to AWQ INT4 + FP8 KV cache reduces serving cost by 72% at less than 1% quality degradation.

This chapter covers every precision format from FP32 to FP4, every quantization technique from naive PTQ to activation-aware algorithms, the outlier problem that breaks naive approaches, the hardware that accelerates each format, and the complete decision framework for choosing a quantization strategy given hardware, model, and quality constraints. 8.1 Floating Point Formats — The Precision Landscape

8.1.1 Number Formats from FP32 to FP4

Every floating point number uses three fields: a sign bit, an exponent (controls range), and a mantissa (controls precision within that range). The fundamental engineering tradeoff: bits given to the exponent widen representable range; bits given to the mantissa improve precision. Every AI format is a different point on this spectrum, chosen for a specific workload characteristic.

8.1.2 Why BF16 Replaced FP16 for Training

The replacement of FP16 by BF16 as the dominant training format was driven by one specific failure mode: overflow. Understanding this concretely is essential because the format choice affects every training run you will ever design.

THE FP16 OVERFLOW PROBLEM: FP16 maximum representable value: 65,504 BF16 maximum representable value: ~3.4 × 10^38 (same as FP32) LLM training gradient scenario: Normal gradient step: 1.2 × 10^4 → FP16 fine (< 65,504) After a learning rate spike or early training instability: Gradient: 8.0 × 10^4 → FP16 OVERFLOW (> 65,504)! Result: gradient → Inf → weight update = NaN → training crash BF16 with 8-exponent bits: same max as FP32 → NEVER overflows in practice THE TRADEOFF (what BF16 sacrifices): FP16: 10 mantissa bits = 3.3 decimal digits of precision BF16: 7 mantissa bits = 2.3 decimal digits of precision For gradient updates: 2.3 decimal digits is SUFFICIENT. Gradients are noisy estimates; sub-1% precision is wasted anyway. For weights: master weights stay in FP32; BF16 just carries the update. Loss scaling (legacy FP16 workaround, now obsolete with BF16): Multiply loss by S=2^15 before backward → gradients are S× larger Divide by S before optimizer step → maintains FP16 range Dynamic S: halve on inf/nan, double on clean step Still needed: FP16 training on pre-Ampere hardware without BF16 support

8.2 Quantization Mathematics

8.2.1 Uniform Affine Quantization — The Foundation

All practical quantization schemes build on a linear mapping from floating-point values to integers. Understanding this foundation precisely — including what fails and why — is the prerequisite for understanding every advanced technique in sections 8.3 and beyond.

QUANTIZATION FORMULA (uniform affine): Q(x) = clamp(round(x / scale + zero_point), q_min, q_max) x_hat = scale × (Q(x) − zero_point) ← dequantization (reconstruction) Where: scale = (max(x) − min(x)) / (q_max − q_min) ← step size zero_point = q_min − round(min(x) / scale) q_min/max = integer bounds (−128 to 127 for INT8 signed) SYMMETRIC QUANTIZATION (zero_point = 0, simpler hardware): scale = max(|x|) / q_max ← anchored at zero Q(x) = round(x / scale) Used by: NVIDIA cuBLAS INT8 GEMM (hardware prefers zero_point=0) ASYMMETRIC QUANTIZATION (zero_point ≠ 0, full range): scale = (max − min) / 255 ← full range utilization Better for activations (ReLU outputs are always positive → asymmetric dist.) Used by: TFLite, ONNX Runtime, activation-quantized deployments QUANTIZATION ERROR: ε = x_hat − x = scale × (round(x/scale) − x/scale) Maximum error: |ε|_max ≤ scale/2 ← half a quantization step WORKED EXAMPLE (INT8 symmetric, weight range [−1, +1]): scale = 1.0 / 127 = 0.00787 Max error = 0.00787/2 = 0.00393 ← 0.4% relative error at max value Error for x=0.001: relative error = 0.00393/0.001 = 393%! ← small values DESTROYED KEY INSIGHT: Quantization error is uniform in absolute terms but catastrophic in relative terms for small values. Outliers force a wide scale, which makes small-magnitude values — potentially equally important — vanish.

8.2.2 Per-Tensor vs Per-Channel vs Per-Group Quantization

The granularity of scale factor computation is one of the most consequential quality-efficiency tradeoffs in quantization engineering. Each level of granularity costs more in metadata storage but recovers more quality.

QUANTIZATION GRANULARITY COMPARISON: Per-Tensor Per-Channel Per-Group (g=128) (1 scale/layer) (1 scale/row) (1 scale/128 weights) ————————————————————————————————————————————————————— Scale factors: 1 per layer N_out scales 70B/128 = 547M scales Scale overhead: Negligible Small ~1.09 GB for 70B model Quality (INT8): Poor Good Excellent Quality (INT4): Unacceptable Marginal Production-acceptable HW compute cost: Lowest Low Medium (dequant per group) Used in: Legacy only Some INT8 libs GPTQ, AWQ, GGUF EXAMPLE — GPTQ INT4 per-group-128 for LLaMA-3 70B: Groups: 70B / 128 = 546,875,000 Scale memory: 546,875,000 × 2 bytes (FP16) = 1.09 GB Total model: 35.0 GB (INT4) + 1.09 GB (scales) = 36.09 GB QUALITY COMPARISON (LLaMA-3 70B, 5-shot MMLU): BF16 baseline: 80.3% INT4 per-tensor (naive): 72.1% ← −8.2% NEVER use INT4 per-group-128 AWQ: 79.5% ← −0.8% Production-acceptable

8.2.3 The Outlier Problem — Why Transformers Break Naive Quantization

Transformer models contain a small but devastating minority of "outlier" activations — values 10–100× larger than typical. These outliers are the primary cause of quality degradation in naive quantization schemes, and every advanced PTQ technique (GPTQ, AWQ, SmoothQuant) exists specifically to address them.

8.3 Post-Training Quantization (PTQ) Techniques

PTQ applies quantization after training is complete, using a small calibration dataset (~128–512 samples) to compute scale factors. No model retraining is required — critical for fast deployment of large models. The three techniques below represent the state of the art for three distinct trade-offs between calibration cost, quality, and outlier handling.

8.3.2 GPTQ — Second-Order Weight Quantization

GPTQ (Frantar et al., 2022) is the breakthrough that made INT4 inference practical. It uses Hessian-based second-order information to compensate for each weight's quantization error in subsequent weights within the same row.

GPTQ ALGORITHM (conceptual): KEY INSIGHT: When weight w_i is quantized to INT4, error ε_i is introduced. Instead of accepting this error, GPTQ adjusts remaining weights in the same row to cancel ε_i's effect on the layer output. For one weight matrix W [out_features × in_features]: 1. Compute Hessian: H = 2 X^T X (X = calibration activations) H[i,i] = sensitivity of output to perturbation of weight column i 2. For each column i (in order of increasing H[i,i]): a. Quantize: W_q[:,i] = INT4_round(W[:,i] / scale) b. Error: ε = W[:,i] − dequant(W_q[:,i]) c. Propagate to remaining: W[:,i+1:] -= (ε × H[i, i+1:]) / H[i,i] Remaining columns are ADJUSTED to compensate for column i's error. 3. Result: INT4 weights where errors are balanced rather than accumulated QUALITY (LLaMA-3 70B, group_size=128): Naive INT4 PTQ: MMLU 71.8% (−8.5%) GPTQ INT4 W4A16: MMLU 79.0% (−1.3%) ← 7.2 points recovery from compensation! COST: Calibration time: ~2–4 hours on 8× H100 for 70B model Storage: 35 GB (INT4 weights) + 1.09 GB (scales) = 36 GB total Tools: AutoGPTQ (HuggingFace), ExLlamaV2, llama.cpp

8.3.3 AWQ — Activation-Aware Weight Quantization

AWQ (Lin et al., 2023) protects the weights that matter most before quantization, rather than fixing errors after. It is generally faster to calibrate than GPTQ and performs comparably or better on models with pronounced outliers.

AWQ CORE ALGORITHM: Observation: ~1% of weight channels correspond to large-magnitude activation channels. These have outsized impact. Protect them; quantize everything else aggressively. Step 1: Identify salient channels Run calibration data → a_i = mean(|X[:,i]|) for each input channel i Top 1% by magnitude = "salient" Step 2: Scale up salient weights, scale down corresponding activations For each salient channel i: W[:,i] *= s_i ← weight uses more of INT4 range X[:,i] /= s_i ← activation compensates (net output: unchanged!) Scale: s_i = mean(|X[:,i]|)^0.5 (geometric mean balances the tradeoff) Step 3: Quantize all weights to INT4 (group_size=128) Salient channels quantize more accurately (use more of range after scaling) Store: INT4 weights + per-channel s_i factors + group scales QUALITY vs GPTQ (LLaMA-3 70B W4A16): AWQ: MMLU 79.5% (−0.8%) Calibration: ~20 min on 8× H100 GPTQ: MMLU 79.0% (−1.3%) Calibration: ~3 hours AWQ wins: 2–3× faster calibration, slightly better quality on outlier-heavy models TOOLS: AutoAWQ (pip install autoawq), TRT-LLM AWQ mode, llama.cpp Q4_K_M

8.3.4 SmoothQuant — Enabling W8A8 Quantization

SmoothQuant (Xiao et al., 2022) enables W8A8 (both weights AND activations in INT8) by migrating the quantization difficulty from activations to weights. This matters when you want full INT8 Tensor Core utilization, not just weight compression.

SMOOTHQUANT MATHEMATICAL INSIGHT: Problem: Activations have large outliers → hard to quantize INT8 Weights are smooth → easy to quantize INT8 Observation: Y = (X diag(s)^{-1}) × (diag(s) W) for ANY scale vector s ↑ smoothed X (easy to quant) ↑ scaled W (slightly harder) Output Y is IDENTICAL because diag(s) and diag(s)^{-1} cancel! Scale selection (α = 0.5 typical): s_i = max(|X[:,i]|)^0.5 / max(|W[i,:]|)^0.5 (geometric mean) α→1: migrate more difficulty to weights (activations become smoother) α→0: no migration (original behavior) Result: Both distributions become quantizable to INT8 without outlier harm. QUALITY (LLaMA-3 70B W8A8): Naive W8A8 INT8: MMLU 75.1% (−5.2%) ← fails SmoothQuant W8A8 INT8: MMLU 79.6% (−0.7%) ← acceptable! THROUGHPUT: INT8 W8A8 on H100: ~1.5× BF16 (INT8 Tensor Cores) NOTE: FP8 via Transformer Engine is now preferred over SmoothQuant INT8 on H100+. SmoothQuant remains the best option for A100 and non-H100 hardware.

8.4 FP8 and the NVIDIA Transformer Engine SHIPPED

The H100 Transformer Engine (TE) is NVIDIA's hardware+software co-design for automatic FP8 mixed precision. It is the simplest and most effective quantization approach on H100+ hardware: replace one import, wrap training in one context manager, achieve 2× GEMM throughput with less than 0.3% quality loss.

TRANSFORMER ENGINE ARCHITECTURE: Without TE (BF16): QKV GEMM: BF16 × BF16 → BF16 (989 TFLOPS peak) FFN GEMM: BF16 × BF16 → BF16 With TE (FP8 auto-cast): QKV GEMM: FP8 E4M3 × FP8 E4M3 → FP32 accumulated (~1,979 TFLOPS!) FFN GEMM: FP8 E4M3 × FP8 E4M3 → FP32 (~1,979 TFLOPS!) Norms, activations: BF16 (unchanged at tensor boundaries) HOW TE KEEPS ACTIVATIONS IN FP8 RANGE (±448 max): 1. Monitor: amax_history = rolling max of |activation| over last N steps 2. Scale: scale = 448 / amax_history 3. Cast: X_fp8 = clamp(X_bf16 × scale, −448, +448) 4. GEMM: Y_fp32 = X_fp8 × W_fp8 (Tensor Core FP8 mode) 5. Descale: Y_bf16 = Y_fp32 / (scale_X × scale_W) All steps AUTOMATIC — zero user configuration needed! PYTORCH USAGE (2 changes): import transformer_engine.pytorch as te # Change 1: import self.qkv = te.Linear(d_model, 3*d_model) # Change 2: te.Linear, not nn.Linear with te.fp8_autocast(enabled=True): # Training context output = model(input) # Everything else unchanged! FP8 INFERENCE (TRT-LLM calibration): trtllm-build \ --checkpoint_dir ./llama3-70b-hf \ --quantization fp8 \ --calib_dataset cnn_dailymail \ --calib_batches 512 QUALITY (LLaMA-3 70B FP8 W8A8 vs BF16): MMLU: 80.1% vs 80.3% (−0.2%) ← essentially lossless HellaSwag: 86.9% vs 87.1% (−0.2%) TruthfulQA:44.5% vs 44.7% (−0.2%) ← consistent sub-0.3% across all benchmarks
NVFP4 on Blackwell: The Next Step NVIDIA B200/GB300 introduces native FP4 support (NVFP4: 1 sign, 2 exponent, 1 mantissa bits). Every 16 weights share one FP8 scale factor (block scaling). Throughput: ~4× BF16, ~2× FP8. LLaMA-3 70B benchmark: 6,800 tok/s on B200 vs 2,200 tok/s on H100 with FP8 — a 3.1× improvement, almost entirely from NVFP4 + increased HBM bandwidth. Requires careful calibration; QAT recommended for best quality. ANNOUNCED

8.5 Weight-Only Quantization — W4A16 in Production

W4A16 quantizes weights to INT4 while keeping activations in BF16/FP16. This is the dominant format for memory-constrained inference — maximizing model size per GPU at acceptable quality loss. Understanding exactly when it helps (decode) and when it doesn't (prefill) is essential for production sizing decisions.

W4A16 THROUGHPUT ANALYSIS (LLaMA-3 70B, H100, batch=1 decode): WHY DECODE GAINS FROM W4A16: Decode is memory-bandwidth bound (loads all weights once per token) BF16 decode: 140 GB at 3.35 TB/s = 41.8ms/token (1 GPU, TP=1 hypothetical) INT4 decode: 35 GB at 3.35 TB/s = 10.4ms/token Theoretical speedup: 4× ← matches the 4× memory footprint reduction Reality: dequantize INT4 → BF16 on-the-fly adds ~15% overhead Adjusted decode speedup: ~3.4× WHY PREFILL DOES NOT GAIN FROM W4A16: Prefill is compute-bound (Tensor Cores processing input sequence) Dequantize INT4 → BF16 in SMEM, then BF16 GEMM → SAME compute Dequantization overhead actually makes prefill ~7% SLOWER W4A16 sweet spot: decode-heavy workloads (chatbots, generation) COMPREHENSIVE FORMAT COMPARISON (LLaMA-3 70B, H100 SXM): Format Mem Decode Prefill MMLU GPU Fit ————————————————————————————————————————————————— BF16 140GB 1,100t/s 85Kt/s 80.3% 2 H100 (TP=2) FP8 W8A8 70GB 2,200t/s 170Kt/s 80.1% 1 H100 INT8 SQ 70GB 1,600t/s 95Kt/s 79.6% 1 H100 AWQ INT4 36GB 2,543t/s 78Kt/s 79.5% 1 H100 + 39GB KV headroom! GGUF Q2 ~22GB 4,200t/s — 73.1% Edge/desktop only

8.6 KV Cache Quantization

KV cache quantization is handled independently from weight quantization and deserves separate analysis. Unlike weights — which are static and can be calibrated offline — KV cache values are generated dynamically per request, requiring online quantization with per-head scale computation.

KV CACHE QUANTIZATION MATH (LLaMA-3 70B): Per-token KV memory formula: KV_bytes/token = 2 (K+V) × L × H_kv × d_head × bytes_per_dtype BF16 KV per token: = 2 × 80 × 8 × 128 × 2 bytes = 327,680 bytes = 0.3125 MB FP8 KV per token: = 2 × 80 × 8 × 128 × 1 byte = 163,840 bytes = 0.1563 MB FP8 KV SAVINGS at batch=32, seq=4096: BF16: 0.3125 MB × 4096 × 32 = 40.96 GB FP8: 0.1563 MB × 4096 × 32 = 20.48 GB → 20 GB freed for more requests! vLLM CONFIGURATION: engine_args = AsyncEngineArgs( model="meta-llama/Llama-3-70b", kv_cache_dtype="fp8", # or "int8" quantization="fp8", # weights also FP8 gpu_memory_utilization=0.90, )

8.7 Quantization-Aware Training (QAT)

QAT trains the model WITH quantization simulation active, allowing weights to adapt to quantization error during training. It produces the highest quality quantized models but requires access to the training pipeline — not feasible for most deployments. It is primarily used by model developers before public release, and for NVFP4 on Blackwell where PTQ quality is insufficient.

QAT MECHANISM — FAKE QUANTIZATION: Forward pass: apply simulated quantization x_fake = scale × round(clamp(x/scale, q_min, q_max)) Output: x_fake looks like INT4/FP8 to downstream layers Backward pass: Straight-Through Estimator (STE) Gradient flows through round() as if it were identity d(loss)/dx ← d(loss)/d(x_fake) × 1 (STE approximation) Without STE: gradient of round() is zero almost everywhere → no learning With STE: weights ADAPT to minimize loss under quantization constraints WHY QAT BEATS PTQ: PTQ: weights frozen; quantization error is irreducible given those weights QAT: weights actively reshape their distributions to minimize quantization error WHEN TO USE QAT: ✅ NVFP4 (Blackwell B200) — PTQ quality insufficient for 4-bit float ✅ Very small models (<7B) where PTQ loses >2% quality ✅ Specialized domains where calibration data is limited ✅ Extreme compression (INT2 / INT3) where PTQ always fails ☐ Standard production deployment — AWQ/GPTQ PTQ is sufficient ☐ Large models (70B+) — QAT cost is prohibitive (weeks of training)

8.8 Quantization Evaluation

Rigorous quantization evaluation requires four benchmark tiers. Many teams make the mistake of evaluating only MMLU, missing quality regressions in code generation or long-context coherence that automated benchmarks cannot catch.

QUANTIZATION EVALUATION BENCHMARK SUITE: TIER 1 — Language Modeling (most sensitive): WikiText-2 perplexity (PPL) Target: PPL increase < 1.0 point vs BF16 Why: PPL catches subtle numeric precision loss; MMLU can mask it TIER 2 — Reasoning & Knowledge: MMLU (57 subjects), HellaSwag, ARC-Challenge, TruthfulQA Target: <1.0% average degradation across all four Red flag: TruthfulQA drop >3% ← quantization increases hallucination susceptibility TIER 3 — Generation Quality: MT-Bench (multi-turn rated by GPT-4), HumanEval (code generation) Target: <5% HumanEval degradation; <0.2 MT-Bench points Note: automated benchmarks do NOT catch incoherence or repetition loops TIER 4 — Calibration Sensitivity: Run quantization with 3-4 DIFFERENT calibration datasets PPL variance across calibration sets target: <0.5 High variance = quantization overfitting to calibration data RED FLAGS requiring immediate re-evaluation: PPL increase >2.0 on WikiText-2 MMLU drop >2% TruthfulQA drop >3% HumanEval drop >10% Latency INCREASES after quantization (dequant overhead > throughput gain)

Key Takeaways

Core Concepts
  • BF16 replaced FP16 for training because it shares FP32's 8-bit exponent — same representable range, zero overflow risk — while halving storage. The reduced mantissa (7 vs 10 bits) is acceptable because gradient updates don't require 7 decimal digits of precision.
  • The outlier problem is the primary cause of quantization quality loss in transformers: 0.01% of activations with values up to 100× typical force a wide quantization scale that rounds typical small-magnitude values to zero (100% relative error). Every advanced PTQ algorithm — GPTQ, AWQ, SmoothQuant — exists to address this specific failure mode.
  • Group quantization (scale every 128 weights) is mandatory for INT4 quality. Per-tensor INT4 loses ~8% MMLU on 70B models. Per-group-128 INT4 with AWQ loses less than 1%. The scale storage overhead is only 1.09 GB for 70B — negligible vs the quality recovery.
  • W4A16 helps decode (4× memory bandwidth reduction) but not prefill (compute-bound; dequant adds overhead). FP8 W8A8 helps both (2× GEMM throughput). Choose based on workload: decode-heavy → AWQ INT4; prefill-heavy (RAG, long-context) → FP8 W8A8.
Cost & Productivity Impact
  • AWQ INT4 + FP8 KV cache reduces serving cost from $0.603 to $0.169 per 1M tokens on LLaMA-3 70B — a 72% cost reduction at −1.0% MMLU quality loss. At 10M requests/day, this saves $792K/year on owned hardware. At hyperscaler scale, the savings reach $162M/year per trillion tokens.
  • FP8 KV quantization doubles concurrent user capacity (30 → 60 users at 4K context on H100 with AWQ INT4 weights) with only −0.2% additional MMLU degradation. It is the single most efficient KV optimization available and should be enabled by default in all production vLLM/TRT-LLM deployments.
  • GQA (8 KV heads vs 64) combined with FP8 KV quantization achieves 16× total KV memory reduction vs MHA BF16 baseline, enabling 1,220 concurrent users per H100 vs 80 — a 15× infrastructure multiplier from two architectural choices.
Principal-Level Insight
  • The quantization decision is a hardware-first decision, not an algorithm-first decision. B200 → NVFP4. H100/H200 → FP8 W8A8. A100 → SmoothQuant INT8 or AWQ INT4. AMD MI300X → FP8 (ROCm 6.x+) or AWQ. Applying the wrong algorithm for the hardware can leave 2–4× throughput on the table.
  • Quantization evaluation must include four tiers: perplexity (most sensitive), reasoning benchmarks, generation quality (code, multi-turn), and calibration sensitivity. Teams that only evaluate MMLU will miss regressions in HumanEval (code), TruthfulQA (hallucination), and long-context coherence — all of which quantization degrades disproportionately.
  • Naive INT4 quantization (no groups) is categorically unacceptable in production — it loses 8–9% MMLU on 70B models, far beyond any acceptable quality bar. If a team is using naive INT4, switching to AWQ INT4 with group_size=128 recovers 7+ MMLU points at identical memory footprint. This is the highest-leverage single-line config change in quantization engineering.
