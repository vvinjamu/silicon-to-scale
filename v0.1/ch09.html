Operator Fusion & the Compiler Stack

How Compilers Turn Naive PyTorch into Near-Peak Hardware Performance
Book: AI/ML Infrastructure from Silicon to Scale  |  Author: Venkat Vinjam  |  Cross-ref: Roofline & regimes (Ch 1) · HBM bandwidth (Ch 4) · CUDA kernels/Triton (Ch 7) · Quantization (Ch 8) · Training (Ch 10) · KV cache (Ch 11)
"The most important optimization in deep learning compilers is operator fusion. Every other optimization is either a special case of fusion or a precondition for it."
— Horace He, "Making Deep Learning Go Brrrr From First Principles"

A naive PyTorch model executes each operation — every LayerNorm, every activation, every matrix multiply — as a separate GPU kernel. Each kernel launch carries ~5μs of CPU overhead. Each intermediate result makes a full round-trip through HBM at 3.35 TB/s. A single transformer layer in eager mode executes approximately 80 kernel launches and 120 HBM round-trips, even though the computation theoretically requires only 2 (input → output). The result: models running at 10–20% of theoretical peak despite perfect algorithmic design.

The compiler stack exists to close this gap. Through operator fusion, graph optimization, and code generation, modern DL compilers — TorchInductor, XLA, and TensorRT — routinely close 60–80% of the gap between naive dispatch and hardware limits. Applied together (torch.compile + FP8 + FlashAttention + TRT-LLM), the cumulative gain reaches 5× throughput over PyTorch eager on identical hardware. This chapter explains how — from first principles of HBM round-trips through the full four-layer compilation pipeline.

9.1 The Three Performance Regimes — Diagnose Before Optimizing

Every GPU kernel and every workload falls into one of three performance regimes. Applying the wrong optimization wastes engineering time and can hurt performance. Identifying the regime is the prerequisite for every decision in this chapter.

THE THREE PERFORMANCE REGIMES (from Ch 1 Roofline): REGIME 1: COMPUTE-BOUND Symptom: Tensor Cores fully saturated; HBM bandwidth underused Diagnosis: Arithmetic Intensity > Ridge Point (~295 FLOP/byte H100) Examples: Large-batch prefill GEMM, training forward pass Compiler impact: MINIMAL — computation is the bottleneck, not overhead What TO do: FP8 quantization, larger tile sizes, TC alignment (Ch 7+8) REGIME 2: MEMORY-BANDWIDTH-BOUND Symptom: HBM BW saturated; Tensor Cores mostly idle Diagnosis: Arithmetic Intensity < Ridge Point Examples: Decode at batch=1, LayerNorm, activations, RMSNorm, GEMV Compiler impact: HIGH — operator fusion eliminates HBM round-trips What TO do: Fusion (this chapter), quantization to reduce bytes/token REGIME 3: OVERHEAD-BOUND (Launch/CPU-Bound) Symptom: GPU idle between tiny kernels; CPU dispatch is bottleneck Diagnosis: SM util <30% despite non-trivial work; GPU time << CPU dispatch time Examples: batch=1 decode without CUDA Graphs; many small ops Compiler impact: VERY HIGH — CUDA Graphs + torch.compile eliminate launch overhead What TO do: CUDA Graphs, torch.compile, C++ runtime QUICK DIAGNOSIS: Step 1: nvidia-smi dmon -s u → watch SM utilization during inference Step 2: If SM util <50%: likely overhead-bound or memory-bound Step 3: Nsight Compute Roofline: - Below memory ceiling → memory-bandwidth-bound - Below compute ceiling → compute-bound - Below BOTH but neither saturated → overhead-bound Step 4: DCGM_FI_PROF_SM_ACTIVE vs DCGM_FI_PROF_SM_OCCUPANCY: - Active high, occupancy low → compute or memory bound - Both low → overhead/launch bound

9.2 Operator Fusion — The Foundation of DL Compilation

9.2.1 The HBM Round-Trip Problem

Every unoptimized neural network layer executes as a sequence of separate kernel launches, each with its own HBM read–compute–write cycle. The waste is not in the arithmetic — it is in the truck trips between warehouse and factory floor.

9.2.2 The Factory Metaphor — Why Fusion Works

The clearest mental model for fusion: HBM is a warehouse, SMEM/registers are a factory floor, and HBM transactions are delivery trucks. Separate kernels truck results back to the warehouse between every operation. Fusion keeps data on the factory floor until all work is done.

WITHOUT FUSION — truck the result back between every operation: Warehouse (HBM) → Truck → Factory (registers): x.cos() Factory → Truck → Warehouse: write cos_x Warehouse → Truck → Factory: read cos_x.cos() Factory → Truck → Warehouse: write cos_cos_x ... × 64 applications: 128 truck trips total 99% of time is truck transport, not computation. WITH FUSION — do all operations while the truck is here: Warehouse → Truck → Factory: x Factory: x.cos().cos().cos()...×64 ← all in registers Factory → Truck → Warehouse: result Cost: 2 truck trips TOTAL regardless of N operations. MATHEMATICAL CONSEQUENCE: fused x.cos() × 64 times ≈ same runtime as fused x.cos() × 1 Both limited by: 2 HBM accesses ÷ 3.35 TB/s ≈ 0.3μs (at 1 GB tensor) NOT by: 64 cos() computations ≈ 0.001μs (registers) The 63 extra cos() operations happen at "zero marginal cost." CRITICAL IMPLICATION: GELU is NOT slower than ReLU in a fused kernel. GELU: ~8× more FLOPs than ReLU BUT: Both are memory-bandwidth-bound elementwise ops BOTH cost exactly 2 HBM accesses — the same bottleneck Extra FLOPs vanish into HBM latency.

9.2.4 The Min-Cut Recomputation Problem

Fusion interacts with activation checkpointing in a non-obvious and economically important way. When an operation is fused, its recomputation cost collapses to nearly zero — changing the optimal checkpoint placement dramatically.

MIN-CUT RECOMPUTATION ECONOMICS: UNFUSED RMSNorm recomputation cost: Forward: 5 HBM round-trips (5 kernels) Recomputing in backward: another 5 HBM round-trips Net recompute cost: HIGH — prefer to store activation FUSED RMSNorm recomputation cost: Forward: 1 HBM round-trip (1 fused kernel) Recomputing in backward: another 1 HBM round-trip Net recompute cost: ~ZERO (bandwidth cost = 1 HBM read) Memory saved: entire intermediate tensor (~16 GB across 80 layers LLaMA-3 70B) OPTIMAL POLICY: Fused ops: RECOMPUTE (free recompute, saves memory) Attention: STORE (recomputing flash attention still reads K,V from HBM) GEMM: STORE (compute-expensive to recompute) AOTAutograd MIN-CUT ALGORITHM: Models graph as flow network; finds minimum-cost partition into {save set} and {recompute set} subject to memory budget. Result: 60% memory reduction with <5% extra compute vs naive recompute-all: 60% memory reduction with 30% extra compute Enabling in PyTorch: from torch.utils.checkpoint import checkpoint_wrapper, CheckpointImpl model = checkpoint_wrapper(model, checkpoint_impl=CheckpointImpl.NO_REENTRANT)

9.4 XLA — The Functional Compiler (JAX / TensorFlow)

XLA (Accelerated Linear Algebra) is Google's compiler for JAX and TensorFlow. Its design philosophy differs fundamentally: where TorchInductor works on traced Python graphs, XLA works on HLO (High-Level Operations) — a purely functional, side-effect-free IR with all shapes known at compile time.

9.5 TensorRT — Production Offline Compilation SHIPPED

TensorRT performs exhaustive offline compilation that produces a GPU-specific engine binary. Unlike JIT compilers, TRT benchmarks every available CUDA kernel for every operation shape in the model — a 5–30 minute investment that pays back over millions of inference calls.

TENSORRT 5-PASS OPTIMIZATION PIPELINE: PASS 1: Graph Cleaning Dead code elimination: Remove ops never contributing to output Constant folding: Pre-compute all-constant ops (RoPE inv_freq, attn scale) Redundant elimination: Remove unnecessary transpose/reshape ops PASS 2: Layer Fusion Vertical chain fusion: Conv → BN → ReLU → fused CBR kernel Attention fusion: QKV proj + attention + output proj → one kernel QKV projection fusion: 3 separate Linear → 1 wider GEMM (3× width) Horizontal fusion: Parallel ops merged into batched kernels PASS 3: Precision Assignment Per-layer precision based on calibration data + quality thresholds Mixed: some layers FP16, others INT8/FP8 based on sensitivity PASS 4: Kernel Selection (most expensive, most impactful) Benchmarks ALL cuBLAS GEMM algorithms for each problem shape Benchmarks ALL cuDNN attention variants Selects fastest kernel per op — result: O(1) dispatch at inference Time: 5–30 min for 70B model | Payback: amortized over millions of calls PASS 5: Memory Planning Analyzes tensor lifetimes; assigns shared memory allocations In-place operations where safe Result: 15–25% HBM savings vs naive allocation

9.5.2 TRT-LLM vs torch.compile Performance Gap

WHY TRT-LLM BEATS torch.compile BY 2× (LLaMA-3 70B, H100, FP8, batch=32): PyTorch eager: ~850 tok/s/GPU torch.compile default: ~1,100 tok/s/GPU (+29%) TRT-LLM FP8: ~2,200 tok/s/GPU (+159% vs eager) THREE MECHANISMS EXPLAINING THE GAP: 1. KERNEL SELECTION DEPTH: torch.compile: Triton auto-tunes ~5 tile configurations TRT-LLM: Benchmarks 50+ cuBLAS algorithms per GEMM shape Exhaustive search finds kernels Triton never considers 2. FUSED ATTENTION PLUGIN: torch.compile: Uses Flash Attention through operator dispatch TRT-LLM: Uses gpt_attention_plugin — custom CUDA kernel fusing: QKV GEMM + rotary embedding + masked attention + KV cache write in one GPU kernel pass — eliminates multiple HBM round-trips 3. CUDA GRAPH CAPTURE: torch.compile (reduce-overhead): Captures graphs at first execution TRT-LLM: Captures CUDA Graphs at startup for ALL decode batch sizes + handles continuous batching within graph replay PRODUCTION BUILD (trtllm-build): trtllm-build \ --checkpoint_dir ./llama3-70b-trt-ckpt \ --output_dir ./llama3-70b-engine \ --gpt_attention_plugin float16 \ # Fused attention --quantization fp8 \ --max_batch_size 64 \ --tp_size 2

9.6 NVFuser — NVIDIA's Runtime Fusion Engine SHIPPED

NVFuser is NVIDIA's production fusion compiler embedded directly in PyTorch, generating CUDA C++ rather than Triton. It is particularly effective for complex pointwise+reduction chains in transformer norms.

KEY NVFUSER PATTERNS FOR LLMs: 1. RMSNorm fusion (every LLaMA-family forward pass): Ops: sum(x^2), sqrt(sum/N+eps), divide, multiply by weight Unfused: 5 kernels, 10 HBM round-trips NVFuser: 1 kernel, 2 HBM round-trips → ~4× speedup 2. SiLU + element-wise multiply (SwiGLU / LLaMA MLP): gate = x * sigmoid(x); output = gate * up NVFuser: 1 read (x, up) → compute gate in registers → 1 write → ~2× 3. Residual + RMSNorm: x = x + residual; x = RMSNorm(x) NVFuser: reads x + residual, adds, normalizes, writes — ONE kernel Eliminates residual add as a separate HBM round-trip NVFuser vs TorchInductor: NVFuser: NVIDIA-only; CUDA C++ output; higher ceiling for complex norms TorchInductor: NVIDIA + AMD + CPU; Triton output; easier extension; better for training

9.7 Graph-Level Optimizations

FOUR CLASSIC GRAPH PASSES (applied before code generation): 1. DEAD CODE ELIMINATION (DCE): Training code has dropout, logging, debug stats — all dead in inference. Impact: 5–15% of training ops eliminated in inference graph. Before DCE: x2 = dropout(x1, p=0.1); x3 = x1 + x2; x4 = debug_stats(x3) After DCE: output = x1 + x1 (dropout=0 at eval; debug removed) 2. CONSTANT FOLDING: inv_freq = 1.0 / (10000 ** (arange(0, d, 2) / d)) ← same every step! After folding: inv_freq = CONSTANT([...]) ← zero runtime compute Impact: RoPE positional encodings, attention scale factors → all become constants 3. COMMON SUBEXPRESSION ELIMINATION (CSE): Pre-norm transformers compute layer_norm(x) twice in naive code. CSE: compute once, share result → eliminates duplicate computation 4. LAYOUT PROPAGATION: PyTorch default: row-major [batch, seq, hidden] Tensor Cores prefer: specific A/B matrix layouts Layout pass: inserts one-time transpose rather than per-GEMM conversion Impact: 10–20% GEMM speedup when layout is non-optimal

# GOAL: Classify regime and apply correct compiler fix

# STEP 1: Identify regime with nvidia-smi
nvidia-smi dmon -s u -d 1  # Watch SM utilization every 1 second

# SM util 30-80% → memory-bandwidth-bound (fusion fix)

# STEP 2: Count graph breaks before applying torch.compile
import torch._dynamo as dynamo
model = LLaMAModel(config).cuda().bfloat16()
explanation = dynamo.explain(model)(dummy_input)
print(f"Graphs: {explanation.graph_count}")
print(f"Graph breaks: {explanation.break_count}")
print(f"Break reasons: {explanation.break_reasons}")
# Target: <5 graph breaks. If >10: fix breaks before compiling
# Common reason: "data-dependent control flow" → restructure conditionals
# Common reason: "Unsupported: .item()" → remove .item() from forward()

# STEP 3: Benchmark properly (common mistake: no warmup)
import torch, time

def bench(model, inputs, n_warmup=10, n_bench=100, label=""):
    for _ in range(n_warmup):
        with torch.no_grad(): _ = model(*inputs)
    torch.cuda.synchronize()
    
    times = []
    for _ in range(n_bench):
        s = torch.cuda.Event(enable_timing=True)
        e = torch.cuda.Event(enable_timing=True)
        s.record()
        with torch.no_grad(): _ = model(*inputs)
        e.record()
        torch.cuda.synchronize()
        times.append(s.elapsed_time(e))
    
    times.sort()
    print(f"{label}: p50={times[n_bench//2]:.2f}ms p99={times[int(n_bench*.99)]:.2f}ms")

model_eager = LLaMAModel(config).cuda().bfloat16()
bench(model_eager, inputs, label="Eager")

model_compiled = torch.compile(model_eager, mode="reduce-overhead")
bench(model_compiled, inputs, label="Compiled")  # First call compiles
# IMPORTANT: Measure p50 AND p99. Compilers can improve mean but worsen p99.
# If compiled p99 > eager p99: check for recompilation on variable shapes

# STEP 4: Inspect generated Triton code
import torch._inductor.config as config
config.trace.enabled = True
config.debug.save_output_code = True
# Run one forward pass → generated kernels saved to /tmp/torchinductor_*/
# Look for: fused_ops_0.py, fused_ops_1.py etc.
# Verify fusion: each file should contain multiple operations

# STEP 5: Profile with torch.profiler to see kernel breakdown
from torch.profiler import profile, ProfilerActivity
with profile(activities=[ProfilerActivity.CUDA], record_shapes=True) as prof:
    with torch.no_grad():
        for _ in range(5):
            _ = model_compiled(*inputs)
print(prof.key_averages().table(sort_by="cuda_time_total", row_limit=20))
# Look for: many small kernels → fusion opportunity missed
# Look for: kernel named "fused_*" → torch.compile fusion working
# Look for: "cudaLaunchKernel" overhead → consider CUDA Graphs

# STEP 6: Verify correctness after compilation
with torch.no_grad():
    out_eager = model_eager(*inputs)
    out_compiled = model_compiled(*inputs)
    max_diff = (out_eager - out_compiled).abs().max().item()
    print(f"Max output difference: {max_diff:.6f}")
    assert max_diff < 1e-3, f"Compilation introduced numeric error: {max_diff}"
# Typical compiled vs eager diff: 1e-5 to 1e-4 (numerical rounding only)
# If diff > 1e-3: check for FP16/BF16 precision issues in fused kernel

Key Takeaways

Core Concepts
  • The three performance regimes — compute-bound, memory-bandwidth-bound, and overhead-bound — require different fixes. Compilers primarily target overhead (CUDA Graphs) and memory (fusion). Applying a compiler to a compute-bound workload yields minimal gain. Classify the regime first, always.
  • Operator fusion eliminates HBM round-trips by keeping intermediate results in registers. A 4-op chain (LayerNorm mean/var, normalize, GeLU, Dropout) requires 6.5 GB of HBM traffic unfused but only 2.1 GB fused — a 3× traffic reduction that translates to proportional latency improvement for memory-bound ops.
  • The factory metaphor captures why fused cos()×64 takes the same time as cos()×1: both are limited by 2 HBM accesses. The 63 extra operations happen at zero marginal cost in registers. This also explains why GeLU is not slower than ReLU in a fused context — both cost exactly 2 HBM transactions.
  • Fusion changes the economics of activation checkpointing. Unfused RMSNorm is expensive to recompute (10 HBM trips). Fused RMSNorm is nearly free (2 HBM trips). AOTAutograd's min-cut algorithm exploits this: fused ops become the primary recomputation targets, yielding 60% memory reduction at <5% compute overhead vs 30% for naive recompute-all.
Cost & Productivity Impact
  • The compiler optimization stack delivers 5.2× throughput on identical hardware through four sequential changes: torch.compile (+29%), FP8 quantization (+100%), Flash Attention v3 (+30%), and TRT-LLM migration (+54%). Engineering investment: ~2 weeks. Annual savings on a 256-GPU cluster serving 50B tokens/day: $9.6M.
  • torch.compile delivers 1.2–1.8× speedup with one line of code and 10–30 seconds compile time. This is the highest-ROI optimization available in AI infrastructure: the ratio of gain to engineering effort exceeds nearly any other optimization in this book. Apply it before anything else.
  • TRT-LLM achieves ~2× more throughput than torch.compile on the same hardware for inference — not by being a "better torch.compile" but by exhaustively benchmarking 50+ cuBLAS kernel variants per GEMM shape (Kernel Selection pass) and using fused custom attention plugins. The 1-week migration investment pays back in days at production scale.
Principal-Level Insight
  • Graph breaks are the silent killer of torch.compile performance. Each break costs ~15% of total compiler gain per 10% of operations affected. Run dynamo.explain() before deploying any compiled model and fix every break source. The target is <5 graph breaks per forward pass — anything above 10 suggests torch.compile may not be worth applying at all.
  • XLA and TorchInductor have fundamentally different compilation models, not just different APIs. XLA requires static shapes (all dimensions fixed at compile time); TorchInductor handles dynamic shapes via guard recompilation. For TPU and completely static workloads (fixed-batch inference), XLA's static analysis enables more aggressive optimization. For variable-length inference (the common LLM case), TorchInductor is the correct choice regardless of performance claims.
  • KernelEvolve-style AI-driven search is not a research curiosity — it is the answer to a real scalability problem. When a production system has thousands of custom operators each needing per-hardware optimization, manual expert tuning is infeasible and compiler output is 30–50% below peak. Evolutionary search on dedicated eval clusters closes this gap in hours. Any infrastructure team at Meta/Google/Microsoft scale building custom operators should be building equivalent capability.
